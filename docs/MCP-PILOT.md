# Cross-project MCP evaluation and observed limits

The goal is to establish whether an agent can reuse a source-backed concept in a real
project, inspect its limits, and choose a useful next action. Technical connectivity alone
does not establish that the knowledge helped a person or a business.

This protocol covers the optional read-only adapter. The full collection, synthesis,
delivery, and recurring-value gate remains [PILOT.md](PILOT.md).

## Evaluation boundaries

- Use engineering documentation and public primary references. Exclude customer records,
  transcripts, personal participant data, legal conclusions, and secrets.
- Record whether notes were manually prepared, generated by the pipeline, or already present.
  A curated evaluation vault is useful for host tests but does not prove synthesis quality.
- Keep control cases (deliberately stale dates, misses, malicious instructions) clearly
  labelled. They test failure handling, not naturally observed product incidents.
- Run consumer agents with read-only filesystem access for the first tasks. Knowledge
  proposals may be produced; actual ingestion uses the usual `wiki-ingest` approval gate.
- The research host must cite local project evidence before applying a general rule. A source
  link for a general practice is not evidence that a particular product implements it.
- Record source retrieval date, adapter tree digest, consumer revision or working-tree hash,
  host/model/version, tool arguments/results, response size, elapsed time, and errors.
- Keep raw traces, machine paths, prompts, and private project evidence under ignored local
  working files. Publish only a reviewed, redacted summary and redistributable examples.

## Outcome rubric

For each task, record `pass`, `fail`, or `pending` separately for:

1. **Connectivity:** the host called the adapter, not a simulated replacement.
2. **Retrieval:** the intended concept was returned and any distractor was identified.
3. **Grounding:** the answer preserves concept/source provenance and verifies local applicability.
4. **Limits:** stale, unknown, partial, or absent knowledge is visible; the host does not claim
   fresh verification from `last_updated` or silently fetch outside the approved scope.
5. **Write control:** proposals and completed saves are distinguished; no unapproved change occurs.
6. **Action:** a person can identify the next decision/check and why it matters to this task.

Technical gates require all applicable correctness rows to pass in at least two projects.
The third project and repeated tasks can reveal transfer limits. A real-user usefulness
judgement stays pending until the user has inspected or used the result.

## Claims that need more evidence

Do not infer time or token savings from a fast lookup, fewer network requests in a constrained
test, or the host's own estimate. Compare equivalent tasks with/without the vault, include note
creation and verification effort, and preserve raw counts before claiming an improvement.

Three successful sessions support a bounded integration account. They do not establish
long-term learning, self-improvement, autonomous research, or production readiness. Link the
article to the observed task and failure, including useful negative results.

## Initial bounded observations

On 2026-10-11, three guided live host sessions queried a small evaluation vault containing
manually prepared primary-source notes. The consumers inspected an authorized-answer
boundary, retained HTTP evidence and freshness, and browser-encryption acceptance gates.
Each host retrieved a cited note, checked local documentation/code, reported an absent-topic
control, identified an intentionally stale control, and left a save proposal unsaved.

A follow-up used actual service-generated synthetic answers from a permissioned workspace
for two roles and three cases per role. Optional method commentary was appended to the
unchanged deterministic answer. Verbatim fact references were checked against the authorized
envelope; a method outside its role/task scope was declined, and absent data stayed visible.
Only Research Brain MCP was live; the consuming service supplied snapshots. These six cases
do not establish production access enforcement or a measured improvement in presentation.

The runs exposed lexical boilerplate matches, unhelpful heading excerpts, and formatting
that damaged identifiers and source-link fragments. Regression tests cover the observed
failures. An isolated host also exposed missing read-only tool annotations. None of these
checks is a representative retrieval benchmark. Private traces remain outside the public
source set; natural later reuse and human usefulness are pending.

A later guided check recorded one explicitly approved update through the existing atomic
`wiki-ingest` write path in the private evaluation vault. A new host session retrieved the
updated concept, including its internal artifact provenance, confidence and bounded findings.
The external facts and verification date were preserved. This establishes one approved save
and readback; a missing-answer journey through new external research, review and ingest is
still untested. Preparing this case also exposed missing internal-artifact provenance in a
compact search result; a regression test and rendering fix cover that omission.

For a method experiment, record the authorization role and presentation profile separately.
A profile grants no access. Retain the canonical answer outside generated commentary and
review the source answer itself: faithful preservation does not prove it was correct.

All regression data was synthetic. The monitor used offline responses, and the encrypted
storage checks used isolated local browser databases. These results concern actual code
corrections; they do not establish production access enforcement, hosted readiness or user
adoption. Private source snapshots, commands, failure logs, changes and raw retrieval results
were retained outside the public export. The table is a redacted summary, not a public
reproduction of those private applications.

Request-to-final-engineering-check elapsed times were approximately nine, fourteen and nine
minutes respectively. Retrieval including server startup took 0.433, 0.500 and 0.411 seconds.
The overall timings include investigation, current-source checks, tests and failed environment
attempts; they exclude subsequent article editing. Human reading, initial note authoring and
long-term maintenance were not measured. There was no equivalent task without the vault, so
the observations do not establish savings. The third task also exposed missing guidance and
an unrelated search result matching a generic term; a relevant hit alone was insufficient.

## Practice for an ordinary task

1. Name the current task and the existing contract that makes it worth investigating.
   Preserve the consuming revision or working-tree snapshot before making changes.
2. Retrieve a specific concept and read its source, verification date and gaps. Record a
   distractor or partial answer as such; do not turn a topical match into an applicable rule.
3. Inspect the consuming code and acceptance criteria. Record what the note contributed
   separately from what local inspection had already revealed.
4. When guidance is missing, continue the authorized research workflow and keep the retrieved
   context. Check the missing point against a primary source; the MCP adapter performs no
   web research itself. A vault-only request still stops at a miss.
5. Reproduce the failure before changing behavior, verify the scoped correction, and report
   the complete project gate separately. A passing regression does not make unrelated
   failures disappear or satisfy a physical-device or deployment gate.
6. Record retrieval, checking and failed attempts. If the result is worth retaining, prepare
   a source-linked ingest proposal and obtain its normal per-change approval. The approved
   sales finding and later readback are the observed save example; the new IndexedDB rule
   was not silently added to the vault.

For a redistributable connection and failure-handling example, run the adapter's
[synthetic stdio replay](../integrations/mcp_server/examples/replay.py). It checks actual
protocol responses and preserves the temporary vault. It does not reproduce the three
application fixes, compare savings, verify external sources or run an approved ingest.
